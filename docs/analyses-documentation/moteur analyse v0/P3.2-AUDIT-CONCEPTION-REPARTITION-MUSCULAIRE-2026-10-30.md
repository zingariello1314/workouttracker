# PHASE 1 — AUDIT

## 1.1 Base d’exercices

### Source de vérité
- Fichier canonique : `src/data/exerciseDatabase.js`
- **1 374** entrées, clés = slug textuel (`pompes`, `développé couché`, …), **pas d’`id` numérique** dans la banque
- Champs observés : `name`, `category`, `primaryMuscles[]`, `secondaryMuscles[]`, `equipment`, `description`, `variations`
- Catalogue cardio séparé : `src/data/cardioExerciseCatalog.js` (aussi `primaryMuscles`)

### Identifiants runtime (programme / journal)
Trois familles coexistent :

| Famille | Forme | Exemple live |
| --- | --- | --- |
| IDs programme « classiques » | entiers courts | `101` Tractions pronation, `103` Dips |
| IDs programme créés / banque | `ex_<ts>_<rand>` | puis souvent **hashés** en storage via `convertToStableNumericId` (`src/utils/workoutExerciseIdResolve.js`) → ex. `1433469569` = Tractions australiennes prise serrée |
| IDs banque / GTG | `db_<slug>` | `db_tractions_pronation` (`makeDbExerciseId` / `makeGtgDbExerciseId`) |

La résolution de nom analytique (`resolveExerciseNameForRecap`) lit d’abord `EXERCISE_DB_NAME_BY_ID` (`db_*`), puis `getExerciseNameById`. Sans le registre programme, les hash numériques restent anonymes (« un mouvement ») — déjà constaté en P3.1.

### Anatomie Delavier / ressources anatomiques
- **Aucune occurrence** de « Delavier » dans le dépôt (code + docs indexés).
- Contenu anatomique réel : `src/data/anatomy/anatomyRegistry.js` + `muscleContent/**` — textes pédagogiques Momentum (familles, recrutement, erreurs).
- Pont visuel banque → mesh : `resolveBankItemAnatomy` + `fineMuscleToVisualGroup.js` (libellés fins → `MuscleGroups`).
- **Ces contenus n’alimentent pas** un tableau machine exercice→coefficient musculaire. Ils ne sont pas une source d’attribution pondérée exploitable telle quelle.

### Intégrés / personnalisés / importés
- Banque intégrée : 1 374 entrées avec muscles déclarés.
- Exercices de programme : objets `{ id, name, series, … }` — **souvent sans** `primaryMuscles` / `muscle` (0/57 sur le programme actif live).
- Ajouts exceptionnels (`dailyVariations.additionalExercises`) : peuvent porter `muscleGroup` / `category` (ex. 2026-10-03 « Pompes inclinées », `muscleGroup: "Pectoraux"`).
- Fallback nominatif : `createFallbackExercise` (`exerciseFallback.js`) peut **fabriquer** `primaryMuscles` par heuristique de nom (`isFallback: true`, `confidence`).

### Doublons / homonymes
- Clés banque : noms uniques (0 doublon de `name` dans la DB).
- Programme live : **même libellé, IDs distincts** (ex. « Pompes déclinées » en `104` et `202` ; « Dips » en `103` et `503`). L’identité correcte est l’ID storage, pas le nom.

### Limites
1. Attribution programme = **indirecte** (nom → lookup banque), fragile aux variantes de libellé.
2. Hash IDs exigent le registre programme pour être nommés.
3. Pas de lien stable exercice-programme ↔ entrée banque (`exerciseBankKey` parfois à l’ajout, pas systématique sur l’historique coché).

## 1.2 Attribution musculaire

### Ce qui existe (exploitable)
Chaîne actuelle :

1. Libellés fins FR dans `exerciseDatabase` (`primaryMuscles` / `secondaryMuscles`)
2. Mapping → groupes visuels `MuscleGroups` (`chest`, `back`, `shoulders`, …) via `resolveVisualGroupsFromLabels`
3. Inférence runtime : `inferMuscleLoadRolesForExercise` (`recapMuscleInference.js`)
   - DB trouvée → rôles primary/secondary
   - sinon heuristique regex sur le nom → **tout en primary**, secondary vide
   - sinon `{ primary: [full_body] }`

### Rôles réellement disponibles

| Rôle | Présent dans les données ? | Fiable ? |
| --- | --- | --- |
| Principal (fine + groupe) | Oui | Partiel — la DB met souvent **plusieurs** muscles en `primaryMuscles` (polyarticulaires) |
| Secondaire | Oui (1 325/1 374) | Partiel — mapping incomplet sur certains libellés |
| Stabilisateur | **Non** comme rôle machine | Textes anatomiques seulement ; **ne pas inventer** |
| Absence | Heuristique / `full_body` | Signale l’inconnu, mais aujourd’hui **masqué** en full_body |

### Chiffres banque (démontrés)

| Métrique | Dénominateur | Valeur |
| --- | --- | --- |
| Entrées banque | — | **1 374** |
| Avec `primaryMuscles` non vide | /1 374 | **1 374** |
| Avec `secondaryMuscles` non vide | /1 374 | **1 325** |
| Sans aucun muscle | /1 374 | **0** |
| Multi-primary au niveau **fin** (≥2 libellés) | /1 374 | **373** |
| Primary mappé vers **1** `MuscleGroups` | /1 374 | **1 158** |
| Primary mappé vers **≥2** groupes | /1 374 | **192** |
| Primary **aucun** groupe mappé | /1 374 | **24** |
| ≥1 libellé non mappé (primary ou secondary) | /1 374 | **159** |

Libellés non mappés les plus fréquents : **« Coiffe des rotateurs » (113)**, « Cardio »/« Conditionnement » (20), « Carré des lombes » (6), …

Exemple critique **Pompes** (données réelles) :
- primary fins : Pectoraux, **Triceps**
- secondary : Deltoïdes antérieurs, Core  
→ triceps = primaire en base, pas « simple implication ». Toute pondération qui redistribue 1 rep en 0,42 pec + 0,24 tri + … est une **convention UI**, pas une mesure.

### Moteur actuel de volume (contre-exemple analytique)
`recapMuscleLoadEngine.distributeRepShareAcrossRoles` :
- `PRIMARY_REP_SHARE = 0.74`, `SECONDARY_REP_SHARE = 0.26`
- cas pompes : parts fixes 0,42 / 0,24 / 0,18 / 0,16  

Ces coefficients **n’ont pas de justification empirique documentée** dans le code. Les découvertes `disc_muscle_now` / `disc_muscle_reorient` / parts push-pull actuelles **consomment** `repShareByGroup` → elles héritent de cette fiction de précision (aligné avec le contre-exemple UI fourni).

**Pour P3.2 : ne pas traiter ces parts fractionnaires comme vérité musculaire.**

# PHASE 2 — PROPOSITION DE MODÈLE

## 2.1 Attribution (structure cible)

```text
ExerciseMuscleAttribution {
  exerciseKey          // id storage normalisé
  exerciseName
  groups: [{
    groupId,           // MuscleGroups
    role: 'primary' | 'secondary',   // pas de stabilizer tant que non sourcé
    fineLabels: string[],            // libellés banque ayant mappé ici
  }]
  source: 'bank' | 'exceptional_tag' | 'heuristic_name' | 'unknown'
  confidence: 'high' | 'medium' | 'low' | 'none'
  classificationVersion: 'p32.v1'
  unmappedFineLabels: string[]
}
```

### Règles
1. **Source `bank`** seulement si lookup DB (ou `exerciseBankKey`) réussi **et** ≥1 primary mappé.
2. **Ne jamais** inventer de nouveaux muscles pour combler la banque.
3. Heuristique nom → `confidence: low`, conclusions narratives **restreintes** (ou exclues des claims forts).
4. `unknown` / aucun primary mappé → compté dans « non analysable », **pas** dilué en full_body pour les totaux musculaires.
5. **Aucun coefficient de contribution** (pas de 0,74 / 0,42). Un exercice contribue en **exposition** (jour / séance) et, pour le volume, en **reps classées** primary vs secondary **sans fractionner** une même rep sur N muscles.

### Anti double-comptage (cœur)
Pour une séance avec `R` reps d’un exercice :
- **Volume primary group G** : si G ∈ primary, ajouter `R` dans le seau *primary* de G (si plusieurs primary : **ne pas** additionner `R` à chaque — utiliser soit (a) **jours d’exposition** multi-label, soit (b) flag `multiPrimary: true` + compter `R` une seule fois dans un seau « polyarticulaire » **et** lister les groupes touchés en exposition).
- **Recommandation v1 :**  
  - Métrique A — **exposition** : jour compte 1 pour chaque groupe primary (et séparément secondary) → multi-primary OK (ce n’est pas du volume).  
  - Métrique B — **volume primary** : uniquement si `|primary| === 1` ; sinon volume primary **non attribué** (exclu du total volume, visible en `ambiguousPolyPrimary`).  
  - Métrique C — **volume secondary** : jamais additionné au volume primary ; exposition secondary séparée.

Ainsi une pompe ne devient **pas** 1 rep pec + 1 rep tri.

## 2.3 Prévu × réalisé

### Entrées
- **Réalisé :** checks+reps (+ GTG certain en couche séparée).
- **Prévu :** exercices du snapshot jour **uniquement** (`reliability === high`), attribution via nom/banque.

### Sorties
- Profil d’exposition primary prévu vs réalisé (par groupe, en **jours** et en **counts d’exercices**, pas en % magique).
- Push/pull/haut-bas : axes **indépendants**, valeurs `push|pull|other|mixed|indeterminate` et `upper|lower|full|mixed|indeterminate`.
- Écarts : groupes prévus peu exposés ; groupes réalisés hors plan ; cohérences.

### Garde-fous
- Jour `reconstruct` / `none` : réalisé seul ; flag `planMuscleComparable: false`.
- Absence de donnée ≠ zéro travail.
- Si < N jours snapshot (seuil à caler comme P3.1, ex. 3) → finding `muscle_plan_data_insufficient` (rival possible avec `disc_plan_data_insufficient`).

## 2.4 Interprétation des « déséquilibres »

Le moteur **compare à l’intention** quand elle est connue.  
Il peut décrire une asymétrie du **réalisé** (ex. plus de jours push que pull) **sans** la juger pathologique.

Classes d’écart :
1. Aligné sur la structure du programme  
2. Introduit par la réalisation (skips / hors-plan)  
3. Apparent (données incomplètes / attribution low)  
4. Cohérent avec spécialisation volontaire (si le plan l’indique)  
5. Non interprétable  

**Interdit :** diagnostic santé/blessure ; injonction « équilibre 50/50 ».
