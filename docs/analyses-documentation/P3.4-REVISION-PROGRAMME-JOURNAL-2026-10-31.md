## 2. Architecture du journal

Stockage : `workoutData.programRevisionLog` (même store que les snapshots P3.3).

```
programRevisionLog: {
  provenanceVersion: 'p34.v1',
  journalIntroducedAt: 'YYYY-MM-DD',  // première écriture — pas de rétro-invention
  revisions: [ { revisionId, programId, structureFingerprint, structure, recordedAt,
                 applicableFrom, applicableUntil, source, mutationKind, reliability } ],
  activationEvents: [ { eventId, type: activated|deactivated|deleted, programId,
                        recordedAt, applicableFrom, reliability } ],
  datedExceptions: [ { eventId, dateStr, suppressedExerciseIds, … } ],
  pendingUncertain: [ { … } ]  // échecs de persistance
}
```

**Empreinte** (`normalizeProgramStructure` + FNV-1a) : schedule par jour (ids, originalId, name, series, variantes A/B), restDay, weekAlternation.  
**Ignoré :** `uiEpoch`, `updatedAt`, renommage seul → `metadata_only` (non journalisé comme structure).

Module : `src/utils/programRevisionJournalP34.js`.

## 3. Contrat d’applicabilité temporelle

| Instant | Signification |
| --- | --- |
| `recordedAt` | Quand l’événement a été écrit |
| `applicableFrom` / `applicableUntil` | Intervalle d’applicabilité de la révision |
| Activation events | Quel `programId` était actif à une date |

**Preuves jour (`DAY_PLAN_PROOF`) :**

| Niveau | Condition |
| --- | --- |
| `demonstrated` | Snapshot P3.3 `planCompareEligible` **ou** (activation recorded + révision recorded couvrant la date, ≥ `journalIntroducedAt`) |
| `probable` | Snapshot unverified, ou fiabilité `uncertain` |
| `non_reconstructible` | Date &lt; intro journal, ou pas d’activation/révision couvrante |

Une révision créée aujourd’hui **ne démontre pas** le mois précédent.  
Les prévisions obsolètes sont invalidées au bundle de mutation (`clearFutureProvisionalForecasts`) — **jamais** promues `high` par le journal seul.

## 4. Persistance et récupération

**Ordre sûr (file `mutationChain` dans `useWorkoutPrograms`) :**

1. `prepareProgramMutationBundle` (seal P3.3 sur ancienne structure + append révision/activation + clear forecasts)  
2. `await updateData(..., { strict: true })`  
3. Puis seulement `setPrograms` / `setActiveProgram` + `persistProgramsPartial`

**Si l’étape 2 échoue :** `pendingUncertain` persisté si possible ; pas de claim `recorded` high inventé.  
La mutation UI peut quand même suivre (intention utilisateur) — l’événement reste **uncertain**.

Atomicité vraie cross-stores (workout DB + context programmes) : **non garantie** par l’architecture existante → stratégie uncertain explicite.

## 5. Variations quotidiennes

| Modification | Classification P3.4 |
| --- | --- |
| Édition schedule / exercices programme | Révision **structurelle** |
| `suppressedExercises` / restore | **Exception datée** (`datedExceptions`) |
| Override séries / patterns jour | Exception datée |
| Exercices exceptionnels additionnels | Exception datée (réalisation / supplément) |
| Réalisé (reps/coches) | Réalisation — hors journal structure |

Ne transforme **pas** une variation jour en nouvelle structure globale.

Critères démontrés :

1. Les versions applicables peuvent être déterminées **après** introduction du journal.  
2. Les changements structurels sont étudiables sans inventer de preuves.  
3. Les jours P3.3 proven restent intacts.  
4. Les événements incertains restent étiquetés uncertain.

## 14. Vérifications ciblées de clôture (2026-10-31, soir)

### Failles constatées puis corrigées

| Faille | Correction |
| --- | --- |
| `demonstrated` si seulement activation+révision recorded | `assessApplicabilityContinuity` : demote si `pendingUncertain`, mismatch live/fingerprint ouvert, fiabilité uncertain, intervalle incomplet |
| Échec persist + UI mutée + restart sans filet | `reconcileLiveProgramAgainstJournal` à l’ouverture calendrier ; dates post-rupture ≤ `probable` |
| Empreinte sans intensity/rest ; hash seul | `intensity`/`rest` dans normalize ; `structuresDeepEqual` avant hash |
| Avant/après = 5 jours actifs seuls | `assessBeforeAfterComparability` : solid / limited / insufficient (calendaire, couverture, révisions intercalaires) |

### Invariants garantis (fonctions / tests)

- Continuité → `assessApplicabilityContinuity`, `resolveHistoricalDayPlanFromJournal` — tests « pendingUncertain », « live ≠ fingerprint »
- Persist fail → `markPendingUncertain` + reconcile restart — test « échec persist + UI mutée »
- Empreinte → `normalizeProgramStructure`, `structuresDeepEqual`, `isSameProgramStructure`
- Avant/après → `assessBeforeAfterComparability`, `causalityClaimAllowed: false`

### Limites résiduelles (explicites)

- Atomicité cross-store workout ↔ context programmes : non garantie ; si **aucun** pending ni reconcile n’a pu s’exécuter, la détection live au prochain open reste le filet.
- Étirements / circuits hors empreinte structurelle des séances classiques.
- Dates &lt; `journalIntroducedAt` : toujours `non_reconstructible`.

### Verdict de clôture définitive

**P3.4 clôturé** pour la fiabilité historique contractuelle (demonstrated ≠ présence brute d’événements ; pas de promotion abusive ; analyses avant/après proportionnées).

Aucun commit Git. P3.5 / P3.6 non démarrés.
