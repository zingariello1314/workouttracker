## 3. Porte B — Décomposition des 2,3 s

Attribution export : **actualDuration SidebarPremium ≈ durée des LT (99,4 %)**.  
TodayTab ~0,5 s sur la bande ; SportXpBar / calculateSportXP : 0.

Le coût inclusif vient du **flush React du sous-arbre entier** à chaque tick, pas d’un seul `useMemo` sport (~filtre hebdo) à lui seul. Les modules graphiques Garmin / calendriers / récaps se reconstruisent parce que le parent se re-rend et que `sidebarProps` était une nouvelle référence.

Instrumentation ajoutée (work-spans) :

- `ModuleItem.render` (par `moduleId`)
- `useSidebarData.sport`

## 4. Porte C — Chaîne causale du réarmement

```
setInterval(1s) dans useSidebar
  → setCurrentTime(new Date())
  → SidebarPremium re-render
  → useSidebarData re-exécuté (memos souvent hit)
  → sidebarProps = { ... }  // nouvelle référence
  → ModuleRenderer / ModuleItem memo bypass
  → ~17 modules + ProfileCard3D (+ effets nightMode → 2e setState)
  → ~2300 ms sync sur le main thread
  → ticks accumulés / prochain setState après commit
  → bande continue ~95 s @ ~99 % occupation
```

Deux problèmes découplés, tous deux traités :

1. **Fréquence injustifiée** — tick horloge sur le mauvais nœud React.
2. **Coût excessif** — arbre lourd forcé à suivre ce tick + props instables.
