## 4. Porte C — Calendrier : contradiction P0.8 expliquée

### Cause

1. **Chunking** cédait le main pendant le *build*, mais le **rendu** `CalendarHeatmap` (6000+ lignes) recalculait encore :
   - `aggregateLiftVolumeKgByDate` / `buildYearStrengthLoadReference`
   - `buildDailyTrainingLoadByDate` (seuils)
   - **`dayStripesForDate` × ~30 cellules à chaque commit** ← coût dominant du Module.profiler
2. `setSidebarMonthDays` → re-render monolithe → actualDuration 2–3,5 s.
3. Après **hidden→visible**, la gate/idle relançait le pack (corrélation t≈155024).

L’index et le chunking étaient empruntés ; ils ne suffisaient pas car le coût restant était **rendus + mémos globaux + stripes sync**.

### Correctifs P0.9

| Mesure | Effet |
|---|---|
| Skip liftVolume / strengthYear / seuils dynamiques en embed | Moins de travail historique sync |
| Stripes **précalculées** dans le pack mois | 0× `buildCalendarDayAllStripes` au rendu cellule |
| Yield **après chaque jour** courant | Chunk ≤ 1 intensité |
| Annulation si `document.hidden` | Pas de dump au retour visible sans contrôle |
| Cache pack par `analyticsRevision` | Évite rebuild inutile |

Architecture : préparation → intensités+stripes → cache révision → publication state → rendu lecture seule.
