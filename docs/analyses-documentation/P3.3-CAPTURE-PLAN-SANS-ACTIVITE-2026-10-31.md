## 1. Audit des déclencheurs de capture (avant P3.3)

| Déclencheur | Fichier | Quand | Limite |
| --- | --- | --- | --- |
| `freezeDayPlan` → `ensureDayPlanSnapshot` | `useWorkoutLogic.js` | coche / reps | **Uniquement si perf** |
| `ensureDayPlanSnapshot` | `CalendarHeatmap.handleSave` | sauvegarde séance calendrier | Perf / saisie |
| `calendarMonthPlanSnapshots` | `CalendarHeatmap` + `calendarMonthRestPlanSnapshot.js` | 1ʳᵉ vue du mois | Repos mensuels, pas le détail d’exercices jour |
| Reconstruct | `ensureReconstructedDayPlanSnapshot` | clés de perf sans snapshot | **Réalisé seulement**, jamais le prévu |

**Constats :**

- Journée prévue **sans saisie** → **aucun** `calendarDayPlanSnapshots[date]`.
- Journée repos → pas de snapshot jour (seulement mois).
- Application fermée → **aucune** capture (pas de service worker / cron navigateur).
- Changement de programme → les jours passés **sans** snapshot étaient réécrits à la lecture live.

## 2. Stratégie jours sans activité

Module `calendarPlanCaptureP33.js` :

| `dayKind` | Signification |
| --- | --- |
| `planned_workout` | Exercices prévus figés |
| `planned_rest` | Repos programmé (liste vide) — **≠ séance manquée** |
| `no_program` | Programme applicable sans séance ce jour |
| `unknown_historical` | Passé sans preuve d’applicabilité → **indeterminate** |
| `reconstruct_only` | Uniquement clés de réalisé |

Capture explicite via `capturePlannedDayWithoutActivity` **sans** exiger de reps/coches.

---

## 3. Application fermée

**Réalité :** un navigateur fermé n’exécute rien.

Stratégie fiable mise en place :

1. **À l’ouverture** (`CalendarHeatmap`, effet P3.3) : `reconcilePlanCaptureOnAppOpen`
   - promote des `provisional_forecast` dont la date est passée → `historical_frozen` ;
   - scelle **hier** (et aujourd’hui côté seal) avec le programme actif (**applicabilité prouvée limitée**) ;
   - jours plus anciens sans preuve → `indeterminate` / `unknown_historical` (**pas** le programme actuel collé) ;
   - pose des **prévisions provisoires** sur today…today+2 (rafraîchissables).
2. **Avant changement de programme** : `sealPlanBeforeProgramChange` (API prête ; seal today ± N jours avec preuve).
3. **À la perf** : `ensureDayPlanSnapshot` annoté `captureTrigger: performance`, `historical_frozen`.

Une prévision `provisional_forecast` **n’est pas** une preuve historique définitive.

## 5. Contrat de provenance

Chaque snapshot (nouveau) expose :

- `dateStr`, `capturedAt`, `status` ∈ {`historical_frozen`, `provisional_forecast`, `indeterminate`}
- `dayKind`, `captureTrigger`, `frozen` / `provisional`
- `programId` / `programIdentity`, `exercises[]`
- `plannedRest`, `suppressedExerciseIds`, `provenanceVersion: p33.v1`

**Legacy P3.0** (sans `status`) = traité comme `historical_frozen` (immuable).

Fiabilité comparaison (via `describeDayPlanProvenance` / matrice) :

| Cas | Reliability |
| --- | --- |
| historical_frozen + workout | high |
| planned_rest | known, 0 créneau, pas missed |
| provisional | provisional |
| reconstruct / indeterminate | realized_only / none |

## 10. Limites → P3.4

- Jours **> ~1 jour** avant l’ouverture : sans journal de révisions programme → **indeterminate**, pas de reconstitution.
- Pas d’historique versionné des programmes / variations (P3.4).
- Pas d’exécution hors process navigateur.
- Changement de programme pendant une longue fermeture : seul « hier » est scellé avec confiance limitée.
